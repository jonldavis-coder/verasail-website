A human-in-the-loop checklist for AI agents

Human in the loop means a person reviews, approves or is told at a defined point before an AI agent finishes work that matters. This checklist shows where to put that point.

By Verasail LLC · Published November 16, 2026 · 9 min read

Human in the loop means a person reviews, approves or is told, at a defined point, before an AI agent finishes work that matters. The phrase only helps if you can point to the step, the person and the decision. This checklist is for placing those points on purpose, matched to the risk of each action, and for noticing when a checkpoint has quietly turned into a rubber stamp.

What the phrase is asking for

A person who can open a dashboard after the fact is informed. A person who must approve before a record changes is in the loop. Both can be the right control. They are different controls, and calling both "human in the loop" hides the difference. Decide which one you mean for each action the agent can take.

The aim is proportional. A misspelled label in an internal draft does not need a director's signature. A customer notice, a permission change, a payment or a compliance exception should not run unattended because the draft sounded fluent. Match the check to the cost of a mistake and to how hard the mistake is to undo.

The Orchestration Hub treats these checkpoints as part of the workflow. Compliance monitoring is the companion question: did the check you designed actually run?

Four kinds of human step

Pick one kind for each action. Write it on the role's contract, next to the tools that action uses. AI agent roles is where that contract lives.

  1. Do, then tell. The agent completes the action and notifies a person. Use this when the action is low risk, easy to undo and frequent. Refreshing an internal draft often fits.
  2. Do, then review. The agent completes the action, and a person checks a sample, or checks every item for a period. Use this while you are still learning how the agent behaves.
  3. Ask, then do. The agent prepares the action and waits. Nothing changes until a named person approves. Use this when the action is hard to undo or visible outside the team.
  4. Stop and hand over. The agent does not take the action. It packages the context and assigns the work to a person. Use this when the case is outside the rules you wrote, or when the rules say a person must decide.

A workflow can mix all four. Gathering numbers can be "do, then tell." Publishing them outside the team can be "ask, then do." An unfamiliar exception can be "stop and hand over." The mix is the design. A single slogan is not.

The checklist

Use this before an agent runs a process without a person on every item. A blank line is the work still to do.

The action

  • What exactly can the agent change, send or decide?
  • Can the action be undone, and what does undoing it take?
  • Who is affected if it is wrong: an internal team, a customer, a regulator, or a system of record?

The rule

  • What does a good result look like, in terms a reviewer can check without guessing?
  • Which cases are in bounds, and which cases must stop?
  • Where is that rule written, and who updates it when the business changes?

The person

  • Who is the reviewer, by role, and who covers when they are away?
  • How long may the work wait for them?
  • At the deadline, does it wait, escalate or expire? Pick one and write it down.

The evidence

  • Can the reviewer see the inputs the agent used, not only the proposed output?
  • Can the reviewer see which tools ran and what they returned?
  • Are the approval, the edit and the rejection stored with a name and a time?

The failure

  • What does the agent do when a source is missing, a tool errors or the output fails a check?
  • Who is told, and on which channel?
  • How will you notice that the checkpoint itself failed and the work went past it?

The learning

  • Where do corrections go, so the next run can improve?
  • Who reviews a sample on a schedule after the happy path is trusted?
  • What will show you that the checkpoint has become a rubber stamp?

Pair the list with retraining for the people who direct the agents. The skill is reviewing the work.

Where to put the checkpoint

Place the human step at the last moment a person can still change the outcome cheaply, and no later. Reviewing a draft before it is filed is useful. Reviewing a copy after a customer has already received the notice is a postmortem.

Also place a checkpoint where the agent crosses a trust boundary:

  • From read to write.
  • From an internal draft to a message someone outside the team will see.
  • From a suggestion to a change in the system of record.
  • From a routine case to an exception the instructions do not cover.
  • From one role's output to the next role's action, when that next action is hard to undo.

Orchestration is the right layer for these gates. The gate has to hold when the agent is confident. Confidence is not a control. If the gate depends on a field being present and current, read data quality for AI agents before you trust it. A missing status should stop the action, not slide through an approval screen as a blank.

What a fair review looks like

Reviewers need the context, a clear question and a real way to say no. "Does this look OK?" invites a skim. "Does this notice match the approved template and the current account status? Yes or no" is a review.

Show the source values, the rule that applied and the proposed change. Ask for an explicit decision: approve, edit or reject. Ask for a reason when the reviewer edits or rejects, so the correction can be reused. Do not measure reviewers on speed alone. A target that rewards one-click approval will get one-click approval. Telemetry should show the mix of decisions, how long work waited and how often an edit was needed, so a rubber stamp is visible while you can still change the design.

When to loosen the loop

Start tighter than feels efficient. "Ask, then do" on every item is a reasonable opening period for any new action. Loosen one action at a time, and only when the record supports it.

Move from "ask, then do" toward "do, then review" when all of these are true:

  • The rule is written and has stopped changing every week.
  • A stretch of real cases was approved with little editing, and someone has read the edits.
  • The errors that did happen were caught by a check, not by chance.
  • The action can be undone, or the remaining sample is large enough for the risk you still accept.
  • A named person still owns the rule and still looks at a sample.

Move back to a tighter loop when the source data, the template or the policy changes. A new source is a new system until it earns the same trust. An agentic workforce needs this monitoring because quality moves when instructions and data move.

Keep the record

An approval that is not stored cannot be defended or learned from. Store the proposed action, the inputs it used, the decision, the person and the time. Keep rejections and edits too. They are often the best material you have for the next revision of the rule.

Compliance monitoring watches whether those records exist and whether the control ran, for people and for agents. The checklist above is the design.
